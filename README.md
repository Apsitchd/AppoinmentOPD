# AppointmentOPD
## ระบบนัดหมายและเวชระเบียนผู้ป่วยนอก (Outpatient Department Appointment and Medical Record System)

## 1. ภาพรวมของโปรเจกต์ (Project Overview)

AppointmentOPD เป็นโปรเจกต์ระบบฐานข้อมูลสำหรับบริหารจัดการการนัดหมายและเวชระเบียนผู้ป่วยนอก (OPD) ของคลินิกเอกชนขนาดกลาง โดยพัฒนาฐานข้อมูลด้วย Microsoft SQL Server เพื่อจัดเก็บและบริหารข้อมูลผู้ป่วย แพทย์ แผนก ตารางออกตรวจ การนัดหมาย ประวัติการตรวจ การสั่งยา และข้อมูลการแพ้ยา

ระบบถูกออกแบบให้รองรับการทำงานของบุคลากรหลายฝ่าย ได้แก่ เจ้าหน้าที่เวชระเบียน พยาบาล แพทย์ เภสัชกร เจ้าหน้าที่การเงิน และผู้ดูแลระบบ โดยแต่ละฝ่ายมีหน้าที่และระดับการเข้าถึงข้อมูลที่แตกต่างกัน

วัตถุประสงค์หลักของโปรเจกต์คือการออกแบบและพัฒนาฐานข้อมูลที่มีโครงสร้างชัดเจน ลดความซ้ำซ้อนของข้อมูล รักษาความถูกต้องของข้อมูล และคำนึงถึงความปลอดภัยของข้อมูลสุขภาพและข้อมูลส่วนบุคคลตามแนวทาง PDPA

**ชื่อฐานข้อมูล:** `AppointmentOPD`

**ระบบจัดการฐานข้อมูล:** Microsoft SQL Server

**ภาษา:** T-SQL (Transact-SQL)

## 2. วัตถุประสงค์ของระบบ (Project Objectives)

1. จัดเก็บข้อมูลผู้ป่วยและประวัติการรักษาอย่างเป็นระบบ
2. รองรับการลงทะเบียนผู้ป่วยใหม่และการกำหนดหมายเลข HN
3. จัดการข้อมูลแพทย์ แผนก และตารางออกตรวจ
4. รองรับการจอง เลื่อน และยกเลิกนัดหมาย
5. จัดเก็บประวัติการเข้ารับบริการ (Visit)
6. รองรับการบันทึกการวินิจฉัยและการสั่งยา
7. จัดเก็บประวัติการแพ้ยาของผู้ป่วย
8. คำนวณยอดรวมของรายการยาในใบสั่งยา
9. จัดทำรายงานสำหรับการบริหารจัดการคลินิก
10. กำหนดสิทธิ์ผู้ใช้งานตามหน้าที่
11. ป้องกันการเปิดเผยข้อมูลส่วนบุคคลและข้อมูลสุขภาพโดยไม่ได้รับอนุญาต
12. จัดเก็บประวัติการเข้าถึงข้อมูลเพื่อสนับสนุนการตรวจสอบย้อนหลัง

## 3. ขอบเขตการทำงานของระบบ (System Scope)

ระบบครอบคลุมการทำงานหลักดังต่อไปนี้

### 3.1 การจัดการข้อมูลผู้ป่วย
- ลงทะเบียนผู้ป่วยใหม่
- จัดเก็บหมายเลข HN
- จัดเก็บชื่อ เพศ วันเกิด และข้อมูลติดต่อ
- จัดเก็บประวัติการแพ้ยา
- จำกัดการเปิดเผยข้อมูลส่วนบุคคล

### 3.2 การจัดการแพทย์และแผนก
- จัดเก็บข้อมูลแพทย์
- จัดเก็บความเชี่ยวชาญของแพทย์
- กำหนดแผนกที่แพทย์สังกัด
- จัดเก็บตารางออกตรวจ

### 3.3 การจัดการนัดหมาย
- จองคิวตรวจ
- ตรวจสอบข้อมูลนัดหมาย
- ยกเลิกนัดหมาย
- บันทึกสถานะการนัดหมาย
- บันทึกกรณีผู้ป่วยไม่มาตามนัด

### 3.4 การจัดการเวชระเบียน
- บันทึกการเข้ารับบริการ
- บันทึกอาการและข้อมูลการตรวจ
- บันทึกการวินิจฉัย
- เชื่อมโยงข้อมูลผู้ป่วยกับแพทย์ผู้ตรวจ

### 3.5 การจัดการยาและใบสั่งยา
- จัดเก็บข้อมูลยาและราคา
- สร้างใบสั่งยา
- เพิ่มรายการยาในใบสั่งยา
- คำนวณยอดรวมของใบสั่งยา
- ตรวจสอบประวัติการแพ้ยา

### 3.6 การจัดทำรายงาน
- รายงานนัดหมายประจำวัน
- รายงานจำนวนผู้ป่วยแยกตามแผนก
- รายงานข้อมูลสำหรับฝ่ายการเงิน
- รายงานคิวจ่ายยาสำหรับเภสัชกร
- รายงานข้อมูลผู้ป่วยในรูปแบบที่จำกัดข้อมูลส่วนบุคคล

## 4. โครงสร้างฐานข้อมูล (Database Structure)

ฐานข้อมูล AppointmentOPD ประกอบด้วย 12 ตาราง แบ่งตามหน้าที่ในการจัดเก็บข้อมูล ดังนี้

### 4.1 ตาราง Department

ใช้จัดเก็บข้อมูลแผนกต่าง ๆ ภายในคลินิก เช่น อายุรกรรม กุมารเวชกรรม และแผนกอื่น ๆ

วัตถุประสงค์:
- จัดเก็บชื่อแผนก
- จัดเก็บรายละเอียดของแผนก
- ใช้เชื่อมโยงข้อมูลแพทย์กับแผนก

เหตุผลที่ต้องมี:
เพื่อให้สามารถแบ่งประเภทการให้บริการและจัดทำรายงานจำนวนผู้ป่วยในแต่ละแผนกได้

### 4.2 ตาราง Doctor

ใช้จัดเก็บข้อมูลแพทย์

วัตถุประสงค์:
- จัดเก็บชื่อแพทย์
- จัดเก็บความเชี่ยวชาญ
- จัดเก็บเบอร์โทรศัพท์
- เชื่อมโยงแพทย์กับแผนก

เหตุผลที่ต้องมี:
เพื่อระบุแพทย์ผู้ให้บริการและใช้ตรวจสอบตารางออกตรวจและการนัดหมาย

### 4.3 ตาราง Patient

ใช้จัดเก็บข้อมูลผู้ป่วย

วัตถุประสงค์:
- จัดเก็บรหัสผู้ป่วย (PatientID)
- จัดเก็บหมายเลข HN
- จัดเก็บเลขประจำตัวประชาชน
- จัดเก็บชื่อ เพศ และวันเกิด
- จัดเก็บเบอร์โทรศัพท์และที่อยู่
- จัดเก็บข้อมูลเกี่ยวกับการจำกัดการจองออนไลน์

เหตุผลที่ต้องมี:
เป็นตารางหลักสำหรับเชื่อมโยงข้อมูลผู้ป่วยกับการนัดหมาย ประวัติการตรวจ และใบสั่งยา รวมถึงเป็นจุดสำคัญในการรักษาความปลอดภัยของข้อมูลส่วนบุคคล

### 4.4 ตาราง Appointment

ใช้จัดเก็บข้อมูลการนัดหมายระหว่างผู้ป่วยกับแพทย์

วัตถุประสงค์:
- จัดเก็บผู้ป่วยที่ทำการนัดหมาย
- ระบุแพทย์และแผนก
- จัดเก็บวันและเวลานัดหมาย
- จัดเก็บสถานะการนัดหมาย

เหตุผลที่ต้องมี:
เพื่อบริหารจัดการคิวตรวจ ป้องกันการนัดหมายซ้ำ และตรวจสอบประวัติการนัดหมายของผู้ป่วย

### 4.5 ตาราง Visit

ใช้จัดเก็บข้อมูลการเข้ารับบริการจริงของผู้ป่วย

วัตถุประสงค์:
- เชื่อมโยงผู้ป่วยกับการเข้ารับบริการ
- เชื่อมโยงแพทย์ผู้ตรวจ
- จัดเก็บข้อมูลการตรวจ
- จัดเก็บข้อมูลการวินิจฉัยและสัญญาณชีพตามโครงสร้างที่กำหนด

เหตุผลที่ต้องมี:
เนื่องจากการนัดหมายกับการเข้ารับบริการจริงเป็นคนละเหตุการณ์กัน จึงต้องแยกข้อมูลออกจากกันเพื่อให้สามารถตรวจสอบประวัติการรักษาได้อย่างถูกต้อง

### 4.6 ตาราง Drug

ใช้จัดเก็บข้อมูลยา

วัตถุประสงค์:
- จัดเก็บชื่อยา
- จัดเก็บรายละเอียดของยา
- จัดเก็บราคา
- ใช้เป็นข้อมูลอ้างอิงในรายการสั่งยา

เหตุผลที่ต้องมี:
เพื่อให้สามารถจัดการข้อมูลยาเป็นศูนย์กลาง ลดการบันทึกชื่อยาและราคาซ้ำในแต่ละใบสั่งยา

### 4.7 ตาราง Prescription

ใช้จัดเก็บข้อมูลใบสั่งยา

วัตถุประสงค์:
- จัดเก็บข้อมูลใบสั่งยา
- เชื่อมโยงใบสั่งยากับ Visit
- จัดเก็บข้อมูลการสั่งยา

เหตุผลที่ต้องมี:
เพื่อเชื่อมโยงการสั่งยากับการเข้ารับบริการแต่ละครั้ง และสามารถตรวจสอบย้อนหลังได้

### 4.8 ตาราง PrescriptionDetail

ใช้จัดเก็บรายละเอียดรายการยาในใบสั่งยา

วัตถุประสงค์:
- ระบุรายการยา
- ระบุจำนวนยา
- เชื่อมโยงกับข้อมูล Drug
- เชื่อมโยงกับ Prescription

เหตุผลที่ต้องมี:
ใบสั่งยาหนึ่งใบสามารถประกอบด้วยยาหลายรายการ จึงต้องแยกตารางรายละเอียดออกจากตารางใบสั่งยาเพื่อรองรับความสัมพันธ์แบบหนึ่งต่อหลาย

### 4.9 ตาราง AuditLog

ใช้จัดเก็บประวัติการเปลี่ยนแปลงข้อมูลในระบบ

วัตถุประสงค์:
- จัดเก็บเหตุการณ์ที่เกี่ยวข้องกับการเปลี่ยนแปลงข้อมูล
- ระบุข้อมูลที่เกี่ยวข้องกับการตรวจสอบ
- สนับสนุนการตรวจสอบย้อนหลัง

เหตุผลที่ต้องมี:
เพื่อให้ผู้ดูแลระบบสามารถตรวจสอบเหตุการณ์ที่เกิดขึ้นกับข้อมูล และช่วยเพิ่มความสามารถในการติดตามปัญหาด้านความปลอดภัย

### 4.10 ตาราง DoctorSchedule

ใช้จัดเก็บตารางออกตรวจของแพทย์

วัตถุประสงค์:
- ระบุแพทย์ที่ออกตรวจ
- จัดเก็บวันและเวลาออกตรวจ
- ใช้เป็นข้อมูลประกอบการจัดการคิวนัดหมาย

เหตุผลที่ต้องมี:
เพื่อให้ระบบสามารถตรวจสอบช่วงเวลาที่แพทย์ให้บริการ และใช้เป็นข้อมูลประกอบการจองคิว

### 4.11 ตาราง PatientAccessLog

ใช้จัดเก็บประวัติการเข้าถึงข้อมูลผู้ป่วย

วัตถุประสงค์:
- บันทึกเหตุการณ์การเปิดดูข้อมูลผู้ป่วย
- จัดเก็บข้อมูลประกอบการตรวจสอบการเข้าถึง
- สนับสนุนการตรวจสอบการใช้งานข้อมูลสุขภาพ

เหตุผลที่ต้องมี:
ข้อมูลสุขภาพเป็นข้อมูลส่วนบุคคลที่มีความอ่อนไหว จึงจำเป็นต้องสามารถตรวจสอบได้ว่าเกิดการเข้าถึงข้อมูลเมื่อใดและโดยผู้ใช้งานใด

### 4.12 ตาราง PatientAllergy

ใช้จัดเก็บประวัติการแพ้ยาของผู้ป่วย

วัตถุประสงค์:
- เชื่อมโยงผู้ป่วยกับข้อมูลการแพ้ยา
- จัดเก็บรายละเอียดเกี่ยวกับการแพ้ยา
- ใช้เป็นข้อมูลประกอบการตรวจสอบก่อนสั่งยา

เหตุผลที่ต้องมี:
เพื่อช่วยลดความเสี่ยงจากการสั่งยาที่ผู้ป่วยมีประวัติแพ้ และสนับสนุนความปลอดภัยในการรักษา

## 5. Primary Key, Foreign Key และ Constraints

ระบบใช้ข้อกำหนดของฐานข้อมูล (Database Constraints) เพื่อควบคุมความถูกต้องของข้อมูล

### Primary Key (PK)

ใช้กำหนดคอลัมน์ที่สามารถระบุข้อมูลแต่ละแถวได้อย่างไม่ซ้ำกัน

เหตุผลที่ต้องมี:
เพื่อป้องกันข้อมูลซ้ำในระดับแถว และใช้เป็นจุดอ้างอิงในการเชื่อมโยงข้อมูลระหว่างตาราง

### Foreign Key (FK)

ใช้กำหนดความสัมพันธ์ระหว่างตาราง

เหตุผลที่ต้องมี:
เพื่อป้องกันการอ้างอิงข้อมูลที่ไม่มีอยู่จริง เช่น การสร้างนัดหมายโดยอ้างอิง PatientID ที่ไม่อยู่ในตาราง Patient

### UNIQUE

ใช้กำหนดให้ข้อมูลในคอลัมน์ที่ระบุไม่สามารถซ้ำกันได้ เช่น HN หรือเลขประจำตัวประชาชน

เหตุผลที่ต้องมี:
เพื่อป้องกันการลงทะเบียนข้อมูลสำคัญซ้ำกัน

### NOT NULL

ใช้กำหนดให้คอลัมน์ต้องมีข้อมูล

เหตุผลที่ต้องมี:
เพื่อป้องกันการบันทึกข้อมูลสำคัญโดยไม่มีค่า

### CHECK

ใช้กำหนดเงื่อนไขของข้อมูลก่อนบันทึกลงฐานข้อมูล

เหตุผลที่ต้องมี:
เพื่อป้องกันข้อมูลที่ไม่ตรงตามเงื่อนไขทางธุรกิจ เช่น จำนวนหรือราคาที่ไม่ถูกต้อง

### DEFAULT

ใช้กำหนดค่าเริ่มต้นให้กับคอลัมน์

เหตุผลที่ต้องมี:
ช่วยลดการกรอกข้อมูลซ้ำ และทำให้ข้อมูลที่ไม่ได้ระบุค่ามีค่าเริ่มต้นตามที่กำหนด

## 6. Stored Procedures

Stored Procedure คือชุดคำสั่ง SQL ที่ถูกจัดเก็บไว้ในฐานข้อมูลและสามารถเรียกใช้งานซ้ำได้

ระบบมี Stored Procedure จำนวน 8 รายการ

### 6.1 sp_RegisterPatient

ใช้ลงทะเบียนผู้ป่วยใหม่

เหตุผลที่ต้องมี:

## 9. User และ Role Management

ระบบมีการสร้าง Database User และ Database Role เพื่อแบ่งแยกผู้ใช้งานตามหน้าที่

### Database Users

1. usr_Registration
2. usr_Pharmacy
3. usr_Finance
4. usr_Doctor
5. usr_Auditor

### Database Roles

1. Role_Registration
2. Role_Pharmacy
3. Role_Finance
4. Role_Doctor
5. Role_Auditor

### วัตถุประสงค์ของแต่ละ Role

**Role_Registration**

สำหรับเจ้าหน้าที่เวชระเบียนที่รับผิดชอบการลงทะเบียนและจัดการข้อมูลพื้นฐานของผู้ป่วย

**Role_Pharmacy**

สำหรับเภสัชกรที่รับผิดชอบข้อมูลยาและการจัดการใบสั่งยา

**Role_Finance**

สำหรับเจ้าหน้าที่การเงินที่รับผิดชอบข้อมูลที่เกี่ยวข้องกับค่าใช้จ่าย

**Role_Doctor**

สำหรับแพทย์ที่รับผิดชอบข้อมูลการตรวจและการรักษาผู้ป่วย

**Role_Auditor**

สำหรับผู้ตรวจสอบที่ต้องการตรวจสอบข้อมูลและประวัติการใช้งานระบบ

เหตุผลที่ต้องมี:
การแยก User และ Role ช่วยให้สามารถออกแบบการเข้าถึงข้อมูลตามหน้าที่ ลดความเสี่ยงจากการเข้าถึงข้อมูลเกินความจำเป็น และสนับสนุนหลัก Least Privilege

หมายเหตุ: ไฟล์ SQL ต้นฉบับมีคำสั่งสร้าง User, Role และกำหนดสมาชิก Role แต่ยังไม่พบคำสั่ง GRANT, REVOKE หรือ DENY สำหรับกำหนดสิทธิ์การเข้าถึง Object อย่างครบถ้วน

## 10. Data Security และ PDPA

เนื่องจากระบบจัดเก็บข้อมูลผู้ป่วยและข้อมูลสุขภาพ จึงต้องให้ความสำคัญกับการรักษาความปลอดภัยของข้อมูล

### 10.1 Dynamic Data Masking

ใช้ปกปิดข้อมูลบางส่วนเมื่อผู้ใช้งานไม่มีสิทธิ์เห็นข้อมูลเต็ม

ตัวอย่างข้อมูลที่มีการกำหนด Mask ในตาราง Patient ได้แก่
- CitizenID
- Phone
- Address

เหตุผลที่ต้องมี:
เพื่อช่วยลดการเปิดเผยข้อมูลส่วนบุคคลเมื่อมีการเรียกดูข้อมูลผ่านบัญชีที่ไม่ได้รับสิทธิ์ให้เห็นข้อมูลเต็ม

หมายเหตุ: Dynamic Data Masking เป็นการปกปิดการแสดงผล ไม่ใช่การเข้ารหัสข้อมูลจริง

### 10.2 Audit Log

ใช้จัดเก็บประวัติการเปลี่ยนแปลงข้อมูล

เหตุผลที่ต้องมี:
เพื่อสนับสนุนการตรวจสอบย้อนหลังและช่วยติดตามเหตุการณ์ที่อาจส่งผลต่อความถูกต้องหรือความปลอดภัยของข้อมูล

### 10.3 Patient Access Log

ใช้บันทึกประวัติการเข้าถึงข้อมูลผู้ป่วย

เหตุผลที่ต้องมี:
เพื่อให้สามารถตรวจสอบการเปิดดูข้อมูลสุขภาพ ซึ่งเป็นข้อมูลที่มีความอ่อนไหว

### 10.4 SQL Injection Prevention

ควรใช้ Stored Procedure และ Parameterized Queries ในการรับค่าจากผู้ใช้งาน แทนการนำข้อความที่ผู้ใช้กรอกมาต่อเป็นคำสั่ง SQL โดยตรง

เหตุผลที่ต้องมี:
เพื่อลดความเสี่ยงจากการโจมตี SQL Injection ซึ่งอาจทำให้ผู้ไม่หวังดีเข้าถึงหรือแก้ไขข้อมูลในฐานข้อมูลโดยไม่ได้รับอนุญาต

## 11. Business Rules

ระบบมีข้อกำหนดทางธุรกิจที่ใช้เป็นแนวทางในการควบคุมการทำงาน ดังนี้

1. แพทย์หนึ่งคนไม่สามารถมีนัดหมายซ้อนเวลาได้
2. ผู้ป่วยสามารถจองแผนกเดียวกันได้วันละหนึ่งคิว
3. ไม่ควรสั่งยาที่ผู้ป่วยมีประวัติแพ้
4. การยกเลิกนัดหมายต้องดำเนินการก่อนเวลานัดอย่างน้อย 2 ชั่วโมง
5. ผู้ป่วยที่ไม่มาตามนัดครบ 3 ครั้ง จะถูกจำกัดการจองออนไลน์เป็นเวลา 30 วัน
6. เวชระเบียนที่บันทึกแล้วไม่ควรถูกลบโดยไม่มีประวัติการเปลี่ยนแปลง
7. การแก้ไขข้อมูลสำคัญควรสามารถตรวจสอบย้อนหลังได้

ข้อกำหนดเหล่านี้มีไว้เพื่อรักษาความถูกต้องของข้อมูล ลดความผิดพลาดในการให้บริการ และเพิ่มความปลอดภัยให้กับผู้ป่วย

หมายเหตุ: ข้อกำหนดทางธุรกิจเป็นสิ่งที่ระบบต้องรองรับ การมีชื่อ Stored Procedure หรือ Table ที่เกี่ยวข้องไม่ได้หมายความว่าทุกข้อกำหนดได้รับการบังคับใช้ครบถ้วนแล้ว

## 12. Database Relationships

ระบบใช้ความสัมพันธ์ระหว่างตารางเพื่อเชื่อมโยงข้อมูลและลดความซ้ำซ้อน

ความสัมพันธ์หลักของระบบประกอบด้วย

- Department เชื่อมโยงกับ Doctor
- Doctor เชื่อมโยงกับ DoctorSchedule
- Patient เชื่อมโยงกับ Appointment
- Doctor เชื่อมโยงกับ Appointment
- Department เชื่อมโยงกับ Appointment
- Patient เชื่อมโยงกับ Visit
- Doctor เชื่อมโยงกับ Visit
- Visit เชื่อมโยงกับ Prescription
- Prescription เชื่อมโยงกับ PrescriptionDetail

- Patient เชื่อมโยงกับ PatientAllergy
- Patient เชื่อมโยงกับ PatientAccessLog

การกำหนดความสัมพันธ์เหล่านี้ช่วยให้ระบบสามารถติดตามข้อมูลตั้งแต่การลงทะเบียน การนัดหมาย การเข้าตรวจ จนถึงการสั่งยาได้อย่างเป็นระบบ

## 13. การออกแบบฐานข้อมูลและ Normalization

ระบบใช้แนวคิด Relational Database Design และ Normalization เพื่อจัดระเบียบข้อมูล

วัตถุประสงค์ของการทำ Normalization ได้แก่

1. ลดความซ้ำซ้อนของข้อมูล
2. ลดปัญหาการเพิ่มข้อมูลที่ไม่สัมพันธ์กัน
3. ลดปัญหาการแก้ไขข้อมูลหลายตำแหน่ง
4. ลดปัญหาการลบข้อมูลที่อาจกระทบข้อมูลอื่น
5. เพิ่มความถูกต้องและความสอดคล้องของข้อมูล

การแยกข้อมูลผู้ป่วย แพทย์ แผนก การนัดหมาย การตรวจ และใบสั่งยาออกเป็นตารางต่าง ๆ ช่วยให้สามารถจัดการข้อมูลแต่ละประเภทได้ชัดเจนขึ้น

เป้าหมายในการออกแบบคือการจัดโครงสร้างให้สอดคล้องกับหลัก Third Normal Form (3NF)

## 15. Database Backup and Restore

การสำรองและกู้คืนฐานข้อมูลเป็นส่วนสำคัญของการดูแลระบบฐานข้อมูล

**Backup**

ใช้สร้างสำเนาฐานข้อมูลเพื่อป้องกันการสูญหายของข้อมูลจากเหตุการณ์ที่ไม่คาดคิด

**Restore**

ใช้กู้คืนฐานข้อมูลจากไฟล์ Backup เมื่อเกิดปัญหากับฐานข้อมูลหลัก

เหตุผลที่ต้องมี:
ข้อมูลผู้ป่วยและประวัติการรักษามีความสำคัญต่อการให้บริการ จึงต้องมีแนวทางรองรับกรณีฐานข้อมูลเสียหายหรือข้อมูลสูญหาย

ไฟล์ Backup ของโปรเจกต์คือ `AppointmentOPD_Full.bak`

## 19. ข้อจำกัดและงานที่สามารถพัฒนาต่อ (Limitations and Future Improvements)

ระบบสามารถพัฒนาต่อยอดได้ในหลายด้าน เช่น

1. เพิ่ม Trigger สำหรับบันทึก Audit Log โดยอัตโนมัติ
2. เพิ่ม Trigger สำหรับตรวจสอบ Business Rules
3. เพิ่มการกำหนด GRANT, REVOKE และ DENY ให้ครบตามหน้าที่ของแต่ละ Role
4. เพิ่มการเข้ารหัสข้อมูลเลขประจำตัวประชาชนอย่างเหมาะสม
5. เพิ่มระบบตรวจสอบการแพ้ยาก่อนบันทึกรายการสั่งยา
6. เพิ่มระบบบริหารคลังยาและตัดสต็อก
7. เพิ่มระบบจัดการใบเสร็จและการชำระเงิน
8. เพิ่มระบบรายงานโรคที่พบบ่อย 10 อันดับ
9. เพิ่มระบบรายงานยาใกล้หมดอายุ
10. เพิ่มชุดทดสอบทั้งกรณีสำเร็จและกรณีถูกปฏิเสธ
11. เพิ่มแผนสำรองและกู้คืนฐานข้อมูลที่ผ่านการทดสอบจริง
12. เพิ่มเอกสาร ER Diagram, Data Dictionary และ Database Permission Matrix

## 20. สรุปโครงการ (Conclusion)

AppointmentOPD เป็นโปรเจกต์การออกแบบและพัฒนาฐานข้อมูลสำหรับระบบนัดหมายและเวชระเบียนผู้ป่วยนอก โดยให้ความสำคัญกับการจัดเก็บข้อมูลอย่างเป็นระบบ ความถูกต้องของข้อมูล การเชื่อมโยงข้อมูลระหว่างตาราง และความปลอดภัยของข้อมูลส่วนบุคคล

การนำ Primary Key, Foreign Key, Constraints, Stored Procedures, Functions, Views และระบบ User/Role Management มาใช้ ช่วยให้ฐานข้อมูลมีโครงสร้างที่ชัดเจนและรองรับการบริหารจัดการข้อมูลของคลินิกได้เป็นระบบมากขึ้น

นอกจากนี้ยังให้ความสำคัญกับการตรวจสอบย้อนหลัง การจำกัดการเข้าถึงข้อมูล และการสำรองข้อมูล เพื่อเป็นพื้นฐานในการพัฒนาระบบฐานข้อมูลที่มีความน่าเชื่อถือและสามารถต่อยอดไปสู่การใช้งานจริงได้
